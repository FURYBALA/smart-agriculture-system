The actual implementation, function-by-function, with real source
references. This document is written from the source code as
authority — every claim below can be checked against the exact file
and line it describes. Nothing here describes intended or aspirational
behavior.

## Firmware architecture

Both nodes follow the same split: hardware-dependent I/O in the
`.ino`, hardware-independent decision logic in a plain `.h` header with
no Arduino/ESP32 includes. This isn't incidental structure — it's what
makes host-side testing possible at all (`firmware/test/*.cpp`,
compiled with a plain `g++`, no board needed).

### Irrigation state machine

`irrigation_logic.h`'s `PumpState` struct tracks three things:
`pumpOn`, `pumpStartedAt`, `pumpLastFinishedAt`, and critically
`pumpStartedByAuto` — a bool tracking *who* turned the pump on, not
just whether it's on. This exists specifically to close a real race
condition: if the safety cutoff timer were gated on "current mode ==
AUTO" instead, a user switching to manual mid-cycle would silently
disable the cutoff, and the pump could run indefinitely. Instead,
`shouldAutoCutoff()` checks `s.pumpStartedByAuto` — an auto-started
pump is always subject to the timer regardless of later mode switches;
a manually-started pump (`/pump/on`) is never subject to it, only
stopped by an explicit `/pump/off`.

`canStartPump()` additionally enforces a cooldown
(`PUMP_COOLDOWN_MS`, 5 minutes in `config.h`) since the pump last
finished, preventing back-to-back watering cycles.

### Soil ADC processing

`convertSoilRawToPercent(raw, rawDry, rawWet)` reproduces Arduino's
`map()` formula exactly (same integer arithmetic and truncation
direction as the real `map()` call it replaced), then clamps to
[0,100] the way `constrain()` does. It explicitly handles
`rawDry > rawWet` (this sensor reads a *higher* raw ADC value when
*drier*) the same way `map()` does with an inverted range — not a
special case, just the same formula applied to inverted inputs.

### REST API (irrigation node)

| Route | Method | Behavior |
|---|---|---|
| `/sensors` | GET | Returns `{temperature, humidity, soilMoisture, pumpOn, mode}`. `temperature`/`humidity` are explicit JSON `null` (not 0 or NaN) if the last DHT11 read failed |
| `/mode` | GET | `{mode: "auto"\|"manual"}` |
| `/mode` | POST | Body `{"mode": "auto"\|"manual"}`; 400 on missing body, invalid JSON, or invalid mode value |
| `/pump/on` | POST | 409 if not in manual mode; sets `pumpStartedByAuto = false` so it's never subject to the auto timer |
| `/pump/off` | POST | 409 if not in manual mode |

### Vision processing pipeline

`vision_node.ino`'s `runInference()`:
1. `esp_camera_fb_get()` — capture a 96×96 RGB565 frame
2. `preprocessFrame(fb)` — unpack + quantize every pixel (see below)
3. `interpreter->Invoke()` — real TFLite Micro inference
4. `vision_logic::argmaxDequantized(...)` — dequantize the INT8 output
   logits using the *output* tensor's own scale/zero-point (read from
   the interpreter at runtime, never hardcoded) and take the argmax
5. Cache into `latestClass`/`latestConfidence`/`latestAtMillis`,
   served by `GET /latest`

### RGB565 handling — the byte-order bug

`esp32-camera`'s RGB565 output is big-endian per pixel (high byte
first) — reading it through a native `uint16_t*` cast on the
little-endian Xtensa core silently byte-swaps every pixel, with no
crash or error, just wrong colors. `vision_logic::decodeRgb565BigEndian
(highByte, lowByte)` combines the two bytes explicitly in the correct
order, then unpacks the 5-6-5 bit fields into normalized [0,1] R/G/B
values using the exact same `(channel * 255) / maxValue / 255.0f`
chain the original inline code used — a real extraction, not a
reimplementation with different rounding.

### TFLite Micro inference setup

`setupModel()`:
- Allocates the tensor arena (`kTensorArenaSize`, ~250 KB) via
  `heap_caps_malloc(size, MALLOC_CAP_SPIRAM | MALLOC_CAP_8BIT)` —
  PSRAM, not a static array, because a static array this size plus
  WiFi/WebServer's own static buffers overflowed the ESP32's ~320 KB
  of internal DRAM by ~186 KB (caught by the linker in CI)
- Validates `model->version() == TFLITE_SCHEMA_VERSION`
- Registers exactly the 5 ops the trained model uses:
  `Conv2D`, `MaxPool2D`, `Mean` (global average pool), `FullyConnected`,
  `Softmax` — via `MicroMutableOpResolver<5>`, not the full op set,
  keeping the binary smaller
- `interpreter->AllocateTensors()`, then caches `input(0)`/`output(0)`
  tensor pointers

### Quantization

`quantizeChannel(normalized, scale, zeroPoint)` converts a normalized
[0,1] float to the INT8 the model expects:
`round(normalized / scale + zeroPoint)`, clamped to [-128, 127]. The
clamp is a defensive addition — the original inline code cast straight
to `int8_t` with no clamp, which is undefined behavior if a stray
rounding error ever pushed the value out of range; the clamp has zero
effect when the invariant holds (this model's scale/zero-point map
[0,1] exactly onto [-128,127]) and prevents UB if it doesn't.

`scale`/`zeroPoint` for input come from `training_metadata.json`
(`input_quantization`), hardcoded into `class_labels.h` at
conversion time; output scale/zero-point are read from the live
interpreter (`modelOutput->params.scale`/`.zero_point`) since they're
generally different values from the input's.

## Lambda architecture

Four single-responsibility functions, one shared layer
(`common_layer`, just the `json_response`/`_DecimalEncoder` helper —
consolidated so it isn't duplicated across all four function
directories):

**`upload_handler`** (`POST /diagnose`): validates the request body
(`imageBase64` present, is a string, decodes as valid base64 — three
distinct 400 cases, not just a generic catch-all), stores the decoded
image in S3 under `uploads/<uuid>.<ext>`, enqueues
`{diagnosisId, bucket, key}` to SQS, returns `202` with the
`diagnosisId` immediately — inference is not on this request's
critical path.

**`inference_handler`** (SQS-triggered, `BatchSize: 1`): for each
message, downloads the image from S3, preprocesses it
(`Image.open(...).convert("RGB").resize((96,96))`, then the identical
normalize/quantize math as the firmware, using the interpreter's own
`input_details["quantization"]`), runs real inference via
`ai_edge_litert.interpreter.Interpreter` (the successor to
`tflite_runtime`, which has been pulled from PyPI entirely — confirmed
directly, not assumed, via `pip index versions tflite-runtime`
returning no distributions), and writes
`{diagnosisId, status: "complete", diseaseName, confidence}` to
DynamoDB. A `try`/`except` around the whole per-message body writes an
explicit `status: "failed"` record on any exception — the fix for a
real bug where a corrupt image would leave no DynamoDB record at all,
so the client would poll "pending" forever with no way to know
something went wrong.

**`results_handler`** (`GET /diagnose/{diagnosisId}`): reads the
DynamoDB item; returns `{status: "pending"}` if no item exists yet
(not an error), or the full item if it does.

**`chat_handler`** (`GET`/`POST /chat/{sessionId}`): POST validates
`{role, text}` (400 if either is missing), writes with a server-
generated timestamp; GET returns all messages for the session ordered
by the table's range key.

### SQS workflow

`InferenceQueue` (`VisibilityTimeout: 60`) decouples upload from
inference. `upload_handler` has `SQSSendMessagePolicy` scoped to this
one queue; `inference_handler` has `SQSPollerPolicy` (also scoped to
this one queue) and is wired via an `Events: QueueTrigger` SQS event
source in `template.yaml`, not manual polling code.

### S3 lifecycle

`LeafImageBucket` (`smart-agri-leaf-images-<account-id>`) has one
lifecycle rule: `ExpirationInDays: 90`, `Status: Enabled` — confirmed
directly against the live bucket via
`get-bucket-lifecycle-configuration`, not just read from the template.
`upload_handler` has `S3CrudPolicy`, `inference_handler` has the
narrower `S3ReadPolicy` (it only ever reads, never writes, to this
bucket).

### DynamoDB schema

`DiagnosisResultsTable`: hash key `diagnosisId` (String),
`PAY_PER_REQUEST` billing. Items: `{diagnosisId, status, diseaseName?,
confidence?, error?}` — `confidence` is always written as `Decimal`,
never native `float` (DynamoDB's `TypeSerializer` rejects float
outright; `Decimal(str(value))` specifically, not `Decimal(float)`
directly, to avoid float's binary-representation artifacts).

`ChatHistoryTable`: composite key `sessionId` (hash) + `timestamp`
(range, String) — lets a single `Query` retrieve a session's full
message history already ordered by time.

## Flutter architecture

`main.dart` wires up three `Provider`s at the app root:
`Esp32Service`, `GeminiService?` (nullable — null if no API key is
configured), `HistoryDatabase`. `HomeShell` holds an `IndexedStack` of
the 6 screens behind a `NavigationBar`, so switching tabs doesn't
remount a screen (relevant to History's pull-to-refresh design — see
below).

`Esp32Service` wraps every HTTP call to both ESP32 nodes with a 5-
second timeout and consistent error handling: a non-200 status or a
malformed response body both surface as the app's own `Esp32Exception`
type, never a raw `FormatException`. This was a real bug fix — before
it, a truncated/corrupted response body (e.g. from a flaky Wi-Fi hop)
threw a raw `FormatException` that `sensor_dashboard_screen.dart`
interpolated directly into displayed UI text, so a corrupted device
response would have shown the user a raw parser stack trace instead of
a readable message.

### Local persistence

`HistoryDatabase` uses `sqflite`'s plain top-level `openDatabase()`/
`getDatabasesPath()` functions — which is what makes the web fix
(below) possible without touching this file at all. Two tables:
`diagnoses` (source, diseaseName, confidence, symptomDescription,
correctiveMeasures, imagePath, timestamp) and `sensor_snapshots`
(temperature, humidity, soilMoisture, pumpOn, mode, timestamp).

**Web persistence fix**: `sqflite` has zero implementation in a
browser (no platform channels exist there). Found via a real headless-
Chromium (Playwright) test run: History threw `databaseFactory not
initialized` instead of loading, on web only. Fixed entirely in
`main.dart` — `if (kIsWeb) { databaseFactory = databaseFactoryFfiWeb;
}` — because `HistoryDatabase`'s calls already route through whichever
factory is registered globally. Also required generating
`web/sqflite_sw.js` and `web/sqlite3.wasm` once via
`dart run sqflite_common_ffi_web:setup` and committing them as static
assets (not regenerated by `flutter build web` itself).

### Error handling patterns

Consistent through the codebase: catch at the boundary where an
external, potentially-malformed input enters (HTTP response bodies,
DynamoDB items, SQS message bodies), convert to a typed
exception/explicit status, never let a raw parser exception propagate
to a layer that will show it to a user or silently drop a record.

## Security

- Credentials (AWS keys/region, Wokwi CI token) exist only as GitHub
  encrypted repository secrets, referenced via `${{ secrets.X }}`,
  never as literal values in any file
- `.env` (Gemini API key, ESP32 host IPs) is gitignored; confirmed
  never committed by scanning full git history, not just the current
  tree
- Every Lambda's IAM policy is scoped to the one resource it needs by
  name (`S3CrudPolicy`/`S3ReadPolicy` bound to the one bucket,
  `SQSSendMessagePolicy`/`SQSPollerPolicy` bound to the one queue,
  `DynamoDBCrudPolicy`/`DynamoDBReadPolicy` bound to the specific
  table each function owns) — no `Resource: "*"` wildcards anywhere
- `deploy-aws.yml` and `wokwi-simulation.yml` are both
  `workflow_dispatch`-only — neither ever triggers automatically
- One real hardening fix: an early workflow version interpolated
  `${{ secrets.AWS_REGION }}` directly into `run:` shell text instead
  of passing it via `env:` — a documented GitHub Actions anti-pattern
  (the secret's literal value gets substituted into the script before
  the shell runs it). Fixed by passing it as an env var and referencing
  `$REGION_SECRET` instead

## Wokwi setup

`firmware/irrigation_node/wokwi/diagram.json` models the ESP32,
DHT22 (standing in for the DHT11 — Wokwi has no DHT11-specific part),
a potentiometer (standing in for the soil sensor — no capacitive/
resistive soil part exists in Wokwi), and an LED+resistor (standing in
for the relay). The real fix that got this working: the diagram needs
**both** an explicit `["esp32:TX", "$serialMonitor:RX", ...]` /
`["esp32:RX", "$serialMonitor:TX", ...]` connection pair **and** a
top-level `"serialMonitor": {"display": "terminal"}` property — neither
alone is sufficient, confirmed by testing each in isolation. Without
both, the simulation connects and runs but produces zero bytes of
serial output, which is exactly what made this look like an
environment problem before the real cause was isolated (see
[`docs/wokwi-simulation.md`](wokwi-simulation.md) for the full story).

`irrigation_node.ino`'s `setup()` prints `WOKWI_IRRIGATION_READY`
unconditionally, immediately after `Serial.begin()`, before anything
that could hang (Wi-Fi, sensors) runs — giving `wokwi-cli --expect-text`
a short, guaranteed, newline-terminated line to match against
regardless of what happens afterward.
